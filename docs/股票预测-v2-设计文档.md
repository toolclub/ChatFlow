## 0. 结论先行（30 秒版）

| 用户需求 | 能不能做 | 结论 |
|---|---|---|
| 读**全部历史公告** | ✅ 能 | akshare `stock_individual_notice_report` 实测 *ST元道 3 年 506 条、平安银行全历史 1737 条；巨潮 `stock_zh_a_disclosure_report_cninfo` 平安银行回溯到 **1992 年**、1982 条、9.77s |
| 自动识别**定增** | ✅ 能，结构化 | 公告类型字段直接给「增发预案/增发提示性公告/增发获准公告/增发上市公告书」；另有 `stock_qbzf_em()` 全市场增发表（含发行价/发行数/发行方式） |
| 自动识别**减持** | ⚠️ **半能，有口径缺口** | 结构化接口只覆盖**董监高**口径（`stock_ggcg_em`/`stock_hold_management_detail_em`）。**大股东减持**没有结构化源（tushare `stk_holdertrade` 当前 token **无权限**），只能靠公告类型「股东/实际控制人股份减持」+ 标题 + LLM 判定。**这个缺口必须让用户知情**（开放问题 #5） |
| 自动识别**爆雷/负面事件** | ⚠️ **半能，无专用数据集** | akshare **没有**违规/处罚/立案数据集（穷举十余个关键词零命中）；`stock_cg_lawsuit_cninfo` 已损坏（`KeyError: 'records'`）。可用替代：公告类型里原生有「违法违规」「其它风险提示公告」「实施退市风险警示」「股票交易异常波动」「股份质押、冻结」+ `stock_yjyg_em` 业绩预告（`预告类型` 枚举含 **首亏/续亏/预减**）→ 规则命中 + LLM 语义分级 |
| **美股** SEC filings | ✅ 能，质量比 A 股高 | 无需 API key，只要合规 User-Agent。MU 全历史 2758 条 filing（1994 至今）；8-K 的 `items` 字段**直接给 Item 编号**（4.02=财报不可靠=强负面），XBRL `companyfacts` 直接给 `GoodwillImpairmentLoss` 数值 |
| **模型调工具**取数 | ✅ 但**建议编排层直调** | 见 §4：不上 ToolNode，前端照样演出「正在调用 XX 工具」。理由是并发度可控、少一次失败面、省 token |
| **公式全展示** | ✅ 能，但要补管道 | v1 把 ARIMA order/AIC、GARCH α/β、MC 参数**算完就扔了**（`engine.py:91` 只 log 不 return）。v2 加 `ModelParams` 贯穿到 DB + 前端 |
| **7 天 K 线预测** | ✅ 能，但需定义 | v1 只出一条 p50 折线，**不是 K 线**。v2 用蒙特卡洛路径 + 历史影线系数合成**预测蜡烛**（OHLC），逐日流出 |
| **暂停** | ⚠️ **真「冻结续跑」做不到** | 全仓库**零 checkpointer**（grep `checkpoint\|MemorySaver\|PostgresSaver` 零命中）。只能做「取消 + 保留已完成维度 + 续跑剩余维度」，UI 仍叫暂停/继续（开放问题 #7） |
| **删除** | ✅ 能，但**不能靠级联** | 实测 `\d event_log`：**零 FK 约束**。`migrate.py:58-60` 声明的 `ON DELETE CASCADE` 因 `create_all` 先于 migration 执行而**永久 no-op**。删除必须显式 `DELETE FROM event_log WHERE conv_id=:pid` |
| **刷新后继续渲染** | ✅ 免费 | `stream_predict` 的重放对 `SSEEventType` **完全泛型**（`prediction_agent.py:405-432` `_emit` → event_log → eid 游标）。新事件只要走 `_emit` 就自动可重放；但前端 `usePrediction.ts` 和 DB 列要补对应分支 |

**最大风险（提前说）**：A 股「爆雷/大股东减持」**没有权威结构化数据源**，v2 的判定 = 公告类型规则（60% 覆盖）+ 公告标题 LLM 语义判定（剩余 40%）。这比 v1 的 Tavily 情绪打分**可靠得多**（公告是法定披露、有日期、有原文 PDF），但**不是官方处罚数据库**。UI 必须标注口径，不能宣称「已扫描所有违规记录」。

| 商誉减值（A 股） | — | ❌ 无专用集 | 关键词零命中 | 需从 `stock_balance_sheet_by_report_em` 抠「商誉」字段做同比，**本次未验证**，v2 不做 |

**akshare 已知 bug（必须防御）**：`stock_individual_notice_report` 与 `stock_zh_a_disclosure_report_cninfo` 在**结果为 0 条时不返回空表，而是抛 `KeyError`**（前者 `KeyError('代码')`，源码 `akshare/stock_fundamental/stock_notice.py:118` 未判空直接 assign；后者 `KeyError(symbol)`）。**已在 300750/002594/000001 上稳定复现 3 次以上**。
→ 所有调用点必须 `try/except KeyError: return []`。否则**一只干净的好股票（没有任何违规公告）会直接把预测流水线炸掉** —— 这是最反直觉的坑。

### 1.2 美股（SEC EDGAR）

| 数据 | 端点 | 状态 | 实测 |
|---|---|---|---|
| ticker → CIK | `https://www.sec.gov/files/company_tickers.json` | ✅ | 9304 条，MU→723125 |
| 全历史 filing 列表 | `https://data.sec.gov/submissions/CIK{10位}.json` + `filings.files` 分页 | ✅ | MU **2758 条，1994-01-06 至今** |
| 8-K 事件语义 | `filings.recent.items` 字段 | ✅ **无需解析正文** | MU 真实样本 `items='2.02,9.01'`、`'5.03,5.07,9.01'`。Item 4.02=财报不可靠（**强负面**）、5.02=高管变动、2.02=业绩 |

| 减持（美股口径） | form=`4`（内部人交易）、form=`144`（拟售限制性证券，减持前兆） | ✅ 列表层可查 | MU：Form 4 **1598 条**、144 **100 条** |
| 大股东持仓 | form ∈ `SC 13D/13D-A/13G/13G-A` | ✅ | MU 86 条 |
| 商誉减值（数值） | `https://data.sec.gov/api/xbrl/companyfacts/CIK{10位}.json` | ✅ **直接给数** | 4MB、629 个 us-gaap 标签，含 `GoodwillImpairmentLoss`/`AssetImpairmentCharges` |
| 全文检索 | `https://efts.sec.gov/LATEST/search-index?q=…` | ✅（2001 年后） | q="impairment" → 55 hits |

**硬门槛**：必须带 User-Agent，且**不能是 `curl/*` 或 `python-requests/*` 默认签名**（实测 403）。必须显式设 `User-Agent: ChatFlow <联系邮箱>`。
**限流**：官方声明 10 req/s；实测 20 并发 / 11.6s 全 200，无 `X-RateLimit-*` 头。**客户端自己限到 5-8 req/s + 429 指数退避**。
**局限**：Form 4 的**买卖方向/股数/价格不在 submissions.json 里**，要逐条下载 XML 解析 → v2 **只用「近 90 天 Form 4/144 条数」作为减持压力代理指标，不做金额级量化**（诚实标注）。

## 2. 维度体系（v1 12 维 + 扩展 9 维 + 新增 5 维 = 26 维）

现状：`graph/prediction/config.py:75-101` 已有 `NEWS_DIMENSIONS`(12) 和 `NEWS_DIMENSIONS_EXTENSIBLE`(9，注释「MVP 不跑」，**当前是死代码**)，`DIMENSION_LABELS`(21) 已就绪。
`PredictionCriteria.dimensions`（`domain.py:24`）→ `build_initial_state`（`prediction_agent.py:243`）→ `NewsSearchNode.execute`（`news_search_node.py:62-64`）**管道已全通**。
**唯一缺口**：无校验（传垃圾字符串会照跑 Tavily 烧钱）+ 只支持「Tavily 搜索型」一种维度。

### 2.1 v2 统一维度注册表（新增 `graph/prediction/dimensions.py`）

```python
@dataclass(frozen=True)
class Dimension:
    key: str
    label: str            # 中文名
    desc: str             # ← 这句话直接显示在用户的多选界面上（用户要求 #3）
    kind: Literal["search", "data", "hybrid"]
    fetcher: str | None   # kind=data 时对应的取数函数名（也是前端展示的"工具名"）
    markets: tuple        # ("cn_a",) | ("us_stock",) | ("cn_a","us_stock")
    default_on: bool
```

| `seasonality` | 季节性/日历效应 | Tavily | 财报季、春节效应、月末效应等日历规律 | ⬜ |
| `policy_calendar` | 政策事件日历 | Tavily | 未来 7 天内的政策/会议/数据发布日程 | ⬜ |

**合计 26 维**，默认勾选 17 维（12 搜索 + 4 新数据 + 美股 1）。

### 2.3 公告 → 爆雷/定增/减持：三层判定（防 token 打爆的核心）

**问题规模**：平安银行 1737 条、比亚迪 2312 条、*ST元道 3 年 506 条。全喂 LLM 必爆。

**第 1 层 — 纯规则（0 次 LLM，pandas filter，<1s）**
用返回结果里的 **`公告类型` 列**（不是入参 `symbol`——实测入参那套顶层分类命中率极低：300750 用 `symbol='持股变动'` 只有 2 条且是无关的一致行动关系变更）：

| 命中类型 | 判定 |
|---|---|
| 含「减持」（如「股东/实际控制人股份减持」） | `event_type=stake_reduction` |
| 含「增发」（增发预案/提示性/获准/上市公告书/其他增发事项） | `event_type=private_placement` |
| 「实施退市风险警示」「申请撤销风险警示及特别处理」「退市整理期」 | `event_type=st_delisting_risk`，severity=-1.0 |
| 「违法违规」 | `event_type=violation`，进第 3 层做严重度分级 |
| 「股份质押、冻结」「其它风险提示公告」「股票交易异常波动」 | 进候选池（第 2 层） |
| **噪音白名单直接丢弃**：董事会决议、监事会决议、股东大会通知/决议、调研活动、分配预案、审计报告、法律意见书、独董述职、各类管理办法/议事规则、定期报告摘要 | 不进 LLM（实测 *ST元道 506 条里这类占 **60-70%**） |

**第 2 层 — 候选池（仍是规则）**
剩余模糊类型 + 时间窗口（默认**近 24 个月**，可配 `PREDICTION_ANNOUNCE_MONTHS`）→ 实测 *ST元道 3 年剩 **50-80 条**。

**第 3 层 — LLM 精判（仅候选池，分批并发）**
- batch = **25~30 条/次**（实测：batch30 → 14.0s / 1145 prompt + 1057 completion tokens；**batch60 → 55.9s，reasoning_tokens 飙到 2776，有输出截断风险，不用**）
- `asyncio.gather` + `Semaphore(4)`，复用 `search_all_dimensions`（`news_search.py:683-716`）的并发骨架
- 输出契约与现有 `score_sentiment` **同构**：`{"event_type": str, "negative_score": -1..0, "reason": str}` → `analyze_node` 的聚合/展示逻辑可直接复用
- **必须剥离 THINK 前缀**：deepseek-v4-pro 是推理模型，先吐 `\x00THINK\x00`；不剥离会导致 `json.loads` 失败（实测已复现）。照抄 `news_search.py` 的 `delta.startswith(_THINK_PREFIX)` 写法
- 实测质量抽查（*ST元道 10 条真实公告）：模型正确区分「第十次提示可能被重大违法强制退市」(-1.0) / 「账户冻结」(-0.6) / 「董事会决议公告」(0.0，常规治理) / 「股票交易异常波动」(0.0，仅波动说明)。**语义分层合理，未见幻觉**

**成本上界**：80 条候选 ÷ 30 = 3 批 × 并发 → 新增 **~20-40s、~1 万 token/次预测**。可接受（v1 的 12 维 Tavily 已经 90s）。

**缓存**（关键）：新增 `announcement_cache` 表（§8.2）。同一条公告（`symbol+ann_date+title_hash`）**只 LLM 打分一次**，7 天内复跑同一只股票的公告维度 ≈ 0 LLM 调用。

### 2.4 明确不做的
- **不做 PDF 全文解析**：PDF 可下载（实测 200 + `%PDF-1.5`），但容器内**未验证任何 PDF 解析库**，且 2000 条 PDF × 解析 = 数分钟级。v2 **只用标题 + 公告类型**。UI 必须诚实标注：「基于公告标题与类型分类，未解析 PDF 正文」。
- **不做 A 股商誉减值**：无数据集，需从资产负债表抠字段，未验证。
- **不做 Form 4 金额级量化**：只算条数。

## 4. 模型调用工具取数：编排层直调（不上 ToolNode）

### 4.1 结论与理由

用户原话是「模型调用对应的工具去取数据」。**建议改为：编排层按用户勾选的维度直接调用取数函数，但把每一次调用作为 `TOOL_TRACE` 事件实时推给前端**。前端看到的效果**完全一样**（「正在调用 stock_announcements(symbol=002594, months=24)… 返回 388 条，耗时 1.9s」），但工程上更可靠。

**证据与理由**：
1. **预测图本来就没有 ToolNode**：`graph/prediction_agent.py:36-52` 的 import 里没有 `from langgraph.prebuilt import ToolNode`（对比聊天图 `graph/agent.py:58` 才有）；`_build_predict_graph()`（`prediction_agent.py:202-218`）4 个节点全是 `BaseNode.execute`，没有一条边指向工具执行节点。上 ToolNode = 重构整个预测图拓扑 + 重设计契约 E 的 fail-fast 短路边。
2. **没有决策空间**：用户已经在多选框里勾好了维度 —— 调哪个函数是**确定映射**（`Dimension.fetcher`），不需要模型「决定」。让 LLM 再决策一遍只会多一轮 HTTP + 三个新失败面（tool_call JSON 解析失败、参数幻觉、模型漏调）。
3. **并发度失控**：现有 12 维靠 `asyncio.Semaphore(PREDICTION_NEWS_CONCURRENCY=5)`（`config.py:60`）强制限流。改 ToolNode 后并发几个、发哪些由模型一次性决定 —— Tavily/东财必被打爆。
4. **省 token**：26 个工具的 schema 塞进 prompt ≈ 数千 token/次。
5. **用户的真实诉求是「看到工具被调用」，不是「模型自主选工具」** —— 前者用 `TOOL_TRACE` 事件 100% 满足。

**唯一代价**：如果产品上坚持要「模型自己决定调哪个工具」的真实 trace，需要把 `news_search` 节点改造成 LLM+ToolNode 子图 + 重设计短路边 + 重设计 SSE 映射（`prediction_agent.py:471-495` 目前只认 `llm_thinking` / `prediction_event` 两种 custom event）。**不建议在 v2 做**。

### 5.3 新维度怎么进公式（具体到数）

v1 只有一条：`drift_mu_annual = arima_drift + 0.15 * news_sentiment`（`engine.py:291`）。
v2 引入**事件分**，用**统一的饱和函数族**（单调、有界、可解释、不会被一条公告刷爆）：

**通用饱和公式**
```
S = -(1 - exp( -Σᵢ xᵢ·wᵢ / κ ))        S ∈ (-1, 0]
时间衰减  wᵢ = exp(-Δtᵢ / τ)           τ = 45 天（半衰期 ≈ 31 天）
```

**① 爆雷分 S_neg**（κ=2.0）
`xᵢ = |negative_scoreᵢ|`（LLM 给的 -1~0 的绝对值）
> 一条今天的 -1.0 强负面 → `S_neg = -(1-e^{-0.5}) = -0.39`；三条 → -0.78。饱和，不会因为一堆 -0.2 的小事叠成 -1。

**② 定增分 S_pp**（κ=2.0）
`xⱼ = 摊薄比例ⱼ/0.10 + max(0, 折价率ⱼ)/0.20`
（摊薄比例 = 发行股数/总股本；折价率 = (最新价 − 发行价)/最新价。取不到总股本时 `摊薄比例=0.05` 保守兜底并在 UI 标「估算」）
> 即「摊薄 10% + 折价 20%」≈ 满分利空强度 2.0 → `S_pp = -0.63`。

**③ 减持压力分 S_sr**（κ=3.0）
`x_k = 减持占总股本比例_k / 1%`（拿不到比例时按公告条数计 `x_k = 1`）
> 一次今天的 3% 减持 → `S_sr = -(1-e^{-1}) = -0.63`。

**④ 事件综合分 F**
```
F = clamp( 0.5·S_neg + 0.2·S_pp + 0.3·S_sr , -1, 0 )
（权重可配：PREDICTION_EVENT_WEIGHTS，默认 0.5/0.2/0.3）
```

**⑤ 与资讯情绪融合**
```
S_total = (1 − λ)·S_news + λ·F        λ = 0.4（PREDICTION_FILING_WEIGHT）
```
> 理由：公告是**法定披露**，可信度高于 Tavily 抓来的新闻，但只覆盖公司自身事件（不含宏观/地缘），所以给 0.4 不给 0.6。

**⑥ 代入 GBM（漂移 + 波动率双通道）**
```
μ = μ_ARIMA + α·S_total                       α = 0.15
M_news  = 1.5  if |S_news| > 0.7  else 1.0    （v1 已有）
M_event = 1 + k·|min(0, F)|                   k = 0.5 → 最多 ×1.5（新增）
σ = σ_GARCH × M_news × M_event

S_{t+1} = S_t · exp( (μ − ½σ²)·dt + σ·√dt·Z ),  Z~N(0,1),  dt = 1/252
```
> **设计意图**：爆雷不只是「往下走」，更是「不确定性放大」。所以负面事件**同时**压低 μ 和抬高 σ —— 表现在图上就是预测中枢下移 + 置信带明显变宽。这符合业界对事件驱动风险的处理方式。

### 5.4 预测 K 线（OHLC）怎么造出来

v1 只有 p50 折线，**不是 K 线**。v2 从蒙特卡洛路径合成蜡烛：

1. **从历史标定影线系数**（可解释、非拍脑袋）：
   ```
   k_up = mean( (High − max(Open,Close)) / Close )   ← 近 120 根历史 K 线
   k_dn = mean( (min(Open,Close) − Low) / Close )
   ```
2. **每条路径 i、每天 t**：
   ```
   Oᵢ,ₜ = Sᵢ,ₜ₋₁        (t=1 时 = last_close)
   Cᵢ,ₜ = Sᵢ,ₜ
   Hᵢ,ₜ = max(Oᵢ,ₜ, Cᵢ,ₜ) · (1 + k_up)
   Lᵢ,ₜ = min(Oᵢ,ₜ, Cᵢ,ₜ) · (1 − k_dn)
   ```
3. **跨 2000 条路径取中位数** → 该日的预测蜡烛 `(O,H,L,C) = (p50(O), p50(H), p50(L), p50(C))`
4. 同时保留 `p10/p90` 作为置信带（v1 已有）。

诚实标注（写进 UI）：**「预测蜡烛的影线由历史平均影线比例合成，不代表真实日内极值分布」**。

### 5.5 Horizon：7 天到底是几根？

- v1：`PREDICTION_HORIZON_DAYS = 5`（`config.py:39`），`_future_dates` 用 `pd.bdate_range`（`engine.py:238-241`）→ **5 个交易日、跳过周末**。

### 5.6 流式推导：engine.py 怎么边算边推

`compute_node.py:115-120` 现在是 `result = await forecast(...)` 一次性算完，`:180-194` 才发**唯一一条** `FORECAST` + `INFLECTION`。

**最小改动**（不改成 async generator）：给 `forecast()` 加 `on_step: Callable[[dict], Awaitable] | None`，在**已经存在的代码接缝**上调用：

| 接缝 | 行号 | 推的事件 | 内容 |
|---|---|---|---|
| 技术指标算完 | `engine.py:281` | `FORMULA_STEP` | MA/MACD/RSI/BOLL/KDJ 公式 + 参数 + 当前值 |
| ARIMA+GARCH gather 完 | `engine.py:288` | `FORMULA_STEP` ×2 | ARIMA(p,d,q)+AIC+9 组网格；GARCH ω/α/β + 持续性 α+β |
| 事件分算完（新增） | 291 前 | `FORMULA_STEP` | S_neg/S_pp/S_sr/F/S_total 逐项代入数值 |
| **蒙特卡洛逐日** | `engine.py:180-209` **改成按天循环** | `FORECAST_DAY` ×7 | 每天一条：`{day, date, o,h,l,c, p10,p50,p90}` |
| 拐点/置信度算完 | `engine.py:355` | `FORECAST`（终态，v1 已有） | 完整 `ForecastResult` |

**蒙特卡洛改逐日的成本 ≈ 0**：`_monte_carlo` 里 `cum_log = np.cumsum(log_ret, axis=1)`（`engine.py:202`）已经是向量化的，改成 `for t in range(horizon): np.percentile(prices[:, t], p)` 只是把一次 percentile 拆成 7 次，纯 numpy，微秒级。

**明确不做**：不流式推 ARIMA 网格搜索的 9 次拟合。它们在**一个** `asyncio.to_thread` 里（`engine.py:284-285`），拆成 9 次 to_thread 只会增加开销；整个 ARIMA+GARCH+MC 大概率是**低个位数秒**（v1 的 92.6s 几乎全是 12 维资讯搜索）。这里的「实时」价值是**可解释性**（一步步看到公式），不是掩盖等待。

## 7. 状态机 + 暂停 + 删除 + 断点续传

### 7.1 状态机（新增 `paused`）

```
                  ┌──────────── resume ─────────────┐
                  ↓                                 │
 queued ─start_news→ news_searching ─start_infer→ inferring ─finish→ done
   │                     │                            │
   ├──── pause ──────────┼──────────── pause ─────────┤
   │                     ↓                            │
   └──────────────→   paused  ←───────────────────────┘
   │                     │
   ├──── fail ───────────┼──── fail ────→ failed  (final)
   └──── stop ───────────┴──── stop ────→ stopped (final)
```

`fsm/prediction.py` 改动（照抄现有 `|` 多源写法，`:62-64`）：
```python
PAUSED = "paused"                                  # 加进 PredictionStatus 枚举
paused = State()                                   # 非 final
pause  = queued.to(paused) | news_searching.to(paused) | inferring.to(paused)
resume = paused.to(queued)                         # 回 queued，重新走图
stop   = ... | paused.to(stopped)                  # paused 也能直接停
fail   = ... | paused.to(failed)
```
**零 DB 迁移**：`status` 是裸 `String(24)`（`db/models.py:275`），无 CHECK 约束（实测 `\d prediction_snapshots` 确认）。

### 7.2 暂停/恢复：诚实说明「做不到什么」

**做不到**：真正的「图冻结在半路、原地解冻继续」。全仓库 grep `checkpoint|MemorySaver|PostgresSaver|Checkpointer` **零命中**，`predict_graph = _build_predict_graph().compile()`（`prediction_agent.py:202-221`）**没有 `checkpointer=` 参数**。引入 `PostgresSaver` 是一个独立的、有相当风险的基础设施改造（要给聊天图一起改，否则两套图行为不一致）。

**做得到（推荐方案）**：**取消 + 保留已完成维度 + 只续跑剩余维度**
```
pause(pid):
  1. session.graph_task.cancel()            （复用 stop 的现成逻辑 prediction_agent.py:397-403）
  2. FSM → paused，写 DB
  3. 已完成的维度结果已经落库（见下面的前置修复）

resume(pid):
  1. 读 snapshot
  2. done_dims = {d.dimension for d in snap.news_digest + snap.filing_digest if not d.failed}
  3. remaining = criteria.dimensions − done_dims
  4. build_initial_state(... dimensions=remaining, seed_news_digest=已完成结果 ...)
  5. start_prediction_graph()  → gather 节点只跑 remaining（为空时near-instant 直接过）
```

**前置修复（必须先做，否则 pause ≈ stop）**：
现在 `update_prediction_news(snapshot_id, news_digest, ...)`（`news_search_node.py:125`）**只在全部维度跑完后调用一次**。`_on_dimension` 回调（`:87-91`）只发 SSE，**不写 DB**。所以现在 cancel 掉，DB 里一个维度结果都没有。
→ 新增 `db/prediction_store.py::append_prediction_dimension(pid, result)`，在 `_on_dimension` 里调用（JSONB 数组 append，用 `jsonb_set` 或读改写 + 乐观锁）。**这是 pause 有意义的唯一前提**。

**另一个诚实点**：`PredictionSession.stop()` 是硬 `Task.cancel()`，**没有「跑完当前维度再停」的协作检查点**，cancel 可能落在任意一个并发维度的 HTTP 请求中间 → 那个维度的在途工作丢弃。加了增量落库后，损失上限 = **并发度（5）个维度**，可接受。

### 7.3 删除

## 10. 待用户确认的开放问题

| # | 问题 | 推荐答案 |
|---|---|---|
| **1** | 「7 天后的 K 线」= **7 个交易日** 还是 **7 个自然日（≈5 个交易日）**？ | **推荐 7 个交易日**（画 7 根预测蜡烛，视觉上就是「一周多一点」），UI 标注「未来 7 个交易日（约 1.5 自然周）」，并提供 5/7/10 三档 |
| **2** | 公告拉多久历史？（全量 1992 年起 ≈ 2000 条 / 9.8s，vs 近 24 个月 ≈ 300 条 / 1.5s） | **推荐：元数据拉全量**（标题+类型+日期，成本仅 1-2s，用于「历史违规/减持次数」信用画像）；**LLM 只判定近 24 个月**（成本可控）。更早的只做规则统计 |
| **3** | 澄清协议用 **LLM 澄清工具** 还是 **前端多选框**？ | **推荐前端多选框**（§3.1）：LLM 工具有 4 项/8 选项硬上限、由模型决定是否触发、答案要拍平成文本重跑全图。多选框零 LLM 往返、省 10-30s |
| **4** | 某个维度的数据源挂了（akshare 429 / SEC 403）→ **降级还是报错**？ | **推荐维度级降级**：该维度标 `failed` + 在卡片上显示失败原因，其余维度继续，最终结果标注「本次 N/26 维度失败」。**只有行情 preflight 失败才整单 failed**（v1 已是此策略） |
| **5** | **「减持」口径缺口**：结构化接口只有**董监高**；**大股东减持**靠公告标题 + LLM 判定（tushare 高级接口无权限）。接受吗？ | **推荐接受**，并在 UI 明确标注「基于法定披露公告识别，董监高部分有精确金额，大股东部分为标题级识别」。不接受则需 §10-#8 |
| **6** | **「爆雷」口径缺口**：A 股**没有**违规/处罚官方数据集（akshare 零命中，诉讼接口已损坏）。只能用「公司自己披露的风险类公告 + 业绩预告首亏/续亏」。接受吗？ | **推荐接受**。业绩预告 `预告类型` 是硬结构化字段（首亏/续亏），加上公告类型「违法违规/退市风险警示」，覆盖了绝大多数真实爆雷。UI 标注「非监管处罚数据库」 |
| **7** | **「暂停」的真实语义**：无 LangGraph checkpointer，做不到「原地冻结续跑」。只能「取消 + 保留已完成维度 + 续跑剩余维度」（最坏丢弃 5 个在途维度）。接受吗？ | **推荐接受**（UI 仍叫暂停/继续）。真 checkpointer 是独立的基础设施改造（要连聊天图一起改），不建议塞进 v2 |
